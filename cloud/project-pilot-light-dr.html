MegaTicket – AWS Pilot Light Disaster Recovery Architecture

엔터프라이즈급 DR 아키텍처 설계 및 구현 | 대규모 티켓팅 서비스 리전 장애 대응 시스템

1. 프로젝트 개요

MegaTicket은 대규모 실시간 티켓팅 트래픽을 처리하는 엔터프라이즈 서비스입니다. 단일 리전 장애 시에도 서비스를 지속할 수 있도록 AWS Pilot Light Disaster Recovery 아키텍처를 설계하고 구현했습니다.

프로젝트 목적
리전 전체 장애 발생 시 자동으로 DR 리전으로 트래픽을 전환하고, 최소한의 다운타임으로 서비스를 복구할 수 있는 시스템을 구축하는 것입니다. 단순 이론이 아닌, 실제 운영 환경에서 사용 가능한 수준의 엔터프라이즈 아키텍처를 목표로 했습니다.

비즈니스 요구사항

  • RTO (Recovery Time Objective): 15분 이내 서비스 복구
  • RPO (Recovery Point Objective): 최대 5분 이내 데이터 손실 허용
  • 자동화: 수동 개입 최소화, 하지만 치명적 오작동 방지를 위한 승인 절차 포함
  • 비용 효율성: DR 리전은 최소 리소스만 운영하여 비용 최적화

2. 전체 아키텍처

2.1 리전 구조

아키텍처는 두 개의 AWS 리전으로 구성됩니다:

  • 메인 리전 (ap-northeast-2, 서울): 정상 운영 시 모든 프로덕션 트래픽 처리
  • DR 리전 (ap-northeast-1, 도쿄): Pilot Light 상태로 최소 리소스만 운영, 장애 시 즉시 확장 가능한 구조

2.3 컴퓨트 계층

  • EC2 + Auto Scaling Group
    • 메인 리전: 정상 운영 시 Desired Capacity 5, Min 3, Max 10
    • DR 리전: Pilot Light 상태로 Desired/Min 0, Max 10 (장애 시 확장)
    • AMI는 AWS Backup + Cross-Region Copy를 통해 DR 리전에 사전 준비
  • Application Load Balancer (ALB)
    • 메인/DR 리전 각각 ALB 구성, Target Group 분리 관리
    • DR 리전 ALB는 최소 리소스만 할당하되, 즉시 트래픽 수용 가능한 상태 유지

2.4 데이터 계층

  • DynamoDB Global Tables
    • 메인/DR 리전 간 실시간 복제 (최종 일관성)
    • 리전 독립적인 읽기/쓰기 가능, RPO 목표 달성의 핵심
    • 장애 시 DR 리전에서 즉시 데이터 접근 가능
  • S3 Cross-Region Replication
    • 정적 웹 자산(HTML, CSS, JS, 이미지) 자동 복제
    • CloudFront Origin Group을 통한 자동 Failover

2.5 네트워크 및 DNS

  • Route 53 Failover Routing
    • Health Check 기반 자동 Failover (30초 체크 간격)
    • 메인 리전 ALB 헬스 체크 실패 시 DR 레코드로 자동 전환
  • CloudFront Origin Group
    • Main S3를 Primary, DR S3를 Failover로 설정
    • Primary 실패 시 자동으로 DR S3로 전환

3. DR 동작 흐름 (Step-by-Step)

DR 프로세스는 AWS Step Functions를 통해 5단계로 오케스트레이션됩니다. 각 단계는 Lambda 함수로 구현되어 있으며, 실패 시 자동 롤백 로직을 포함합니다.

Step 0: DR 실행 승인 및 중복 실행 방지 (Lock / Approval)

목적: 동시 다중 실행 방지 및 수동 승인을 통한 오작동 방지

  • DynamoDB Lock 테이블에 Execution ID와 Timestamp 기록
  • 기존 실행 중인 DR 프로세스가 있으면 종료 (중복 방지)
  • Slack/Email을 통한 승인 요청 발송 (선택적 수동 승인 옵션)
  • Lock 획득 성공 시 Step 1로 진행, 실패 시 Workflow 종료
설계 의도: 자동화와 안전성의 균형. 완전 자동화는 위험할 수 있으므로, 운영팀이 상황을 확인하고 승인할 수 있는 옵션을 제공합니다. 하지만 실제 운영에서는 CloudWatch Alarm 트리거 시 자동 승인으로 설정할 수 있습니다.

Step 1: 네트워크 및 필수 인프라 준비

목적: DR 리전의 네트워크 환경이 트래픽을 수용할 수 있는지 확인 및 준비

  • VPC, Subnet, Security Group, Internet Gateway 상태 확인
  • 필요 시 NAT Gateway 활성화 (비용 최적화를 위해 Pilot Light 상태에서는 비활성화 가능)
  • ALB Target Group 헬스 체크 설정 확인
  • 모든 인프라가 준비되었는지 검증

Step 2: AMI 기반 ASG Scale-out 또는 복구 인스턴스 기동

목적: DR 리전에 컴퓨트 리소스 확장

  • AWS Backup으로 생성된 최신 AMI 확인 (Cross-Region Copy 완료된 AMI)
  • Auto Scaling Group의 Desired Capacity를 0에서 목표값(예: 5)으로 조정
  • 인스턴스 기동 상태 모니터링 (CloudWatch Metric 기반)
  • 최소 인스턴스 수(예: 2개)가 Healthy 상태가 될 때까지 대기 (Timeout: 10분)
운영 고려사항: 인스턴스 기동 시간을 고려한 충분한 Timeout 설정이 필요합니다. 또한 AMI가 오래되었다면 애플리케이션 초기화 시간이 더 걸릴 수 있으므로, 정기적인 AMI 업데이트가 중요합니다.

Step 3: ALB / Target Group 연결 및 검증

목적: 로드밸런서가 새로 기동된 인스턴스로 트래픽을 라우팅할 수 있도록 설정

  • Target Group에 인스턴스 등록 확인 (Auto Scaling Group에 의해 자동 등록됨)
  • ALB 헬스 체크를 통한 인스턴스 Healthy 상태 확인
  • 최소 2개 이상의 인스턴스가 Healthy 상태일 때까지 대기
  • DR 리전 ALB의 DNS 이름 확인 및 Route 53 레코드 업데이트 준비

Step 4: Route 53 레코드 전환 또는 활성화

목적: 글로벌 트래픽을 DR 리전으로 전환

  • Route 53 Health Check 결과 확인 (메인 리전이 여전히 실패 상태인지 검증)
  • Route 53 Failover 레코드에서 DR 레코드를 Primary로 변경하거나, Weighted Routing을 통해 100% 가중치 부여
  • DNS TTL을 고려한 전파 시간 대기 (일반적으로 30초~1분)
  • DR 리전 ALB로의 트래픽 유입 확인 (CloudWatch Metric)
  • DR Workflow 완료 알림 발송 (Slack/Email)
  • DynamoDB Lock 해제
설계 고려사항: Route 53의 Failover Routing은 Health Check 기반으로 자동 전환되지만, Step Functions를 통해 명시적으로 레코드를 조작함으로써 더 정확한 제어가 가능합니다. 또한 Weighted Routing을 사용하면 점진적 트래픽 전환이나 A/B 테스트도 가능합니다.

3.1 장애 감지 및 트리거

DR Workflow는 다음 경로를 통해 트리거됩니다:

  1. Route 53 Health Check 실패
    • 메인 리전 ALB 헬스 체크가 연속 3회 실패
    • CloudWatch Alarm 상태 변경 → SNS Topic 발행
  2. EventBridge Rule
    • SNS Topic을 EventBridge로 전달
    • EventBridge가 Step Functions State Machine 실행
  3. 수동 실행
    • AWS Console 또는 CLI를 통한 Step Functions 수동 실행 (테스트/운영 목적)

5. Pilot Light DR 설계 의도 및 장점

5.1 DR 전략 선택: Pilot Light vs Warm Standby vs Active-Active

엔터프라이즈 환경에서 DR 전략을 선택할 때는 비용, RTO, RPO, 운영 복잡도를 종합적으로 고려해야 합니다. MegaTicket 프로젝트에서는 Pilot Light 전략을 선택했습니다.

DR 전략 RTO 비용 (월간) 장점 단점
Pilot Light 15분 ~ 1시간 낮음 (~$500) 비용 효율적, 필요한 리소스만 운영 복구 시간이 상대적으로 김
Warm Standby 5분 ~ 15분 중간 (~$2,000) 빠른 복구, 데이터 실시간 동기화 비용이 높음, 리소스 일부 낭비
Active-Active 거의 0분 매우 높음 (~$5,000+) 가장 빠른 복구, 로드 분산 가능 비용 매우 높음, 복잡한 데이터 일관성 관리

5.2 Pilot Light를 선택한 이유

1. 비용 최적화
티켓팅 서비스는 특성상 대부분의 시간 동안 정상 운영되며, 리전 전체 장애는 매우 드물게 발생합니다. Warm Standby나 Active-Active는 평소에도 상당한 리소스를 유지해야 하지만, Pilot Light는 최소한의 리소스(ALB, VPC, DynamoDB Global Tables)만 운영하여 비용을 크게 절감합니다.
2. RTO 목표 달성 가능
요구사항인 RTO 15분은 Pilot Light로 충분히 달성 가능합니다. EC2 인스턴스 기동 시간(3~5분) + 애플리케이션 초기화(2~3분) + DNS 전파(1~2분)를 고려해도 15분 이내 복구가 가능하며, Step Functions 기반 자동화로 수동 작업 시간을 최소화했습니다.
3. RPO 목표 달성 (DynamoDB Global Tables)
DynamoDB Global Tables를 사용함으로써 데이터는 실시간으로 복제되며, RPO 목표인 최대 5분 이내 데이터 손실을 충족합니다. 이는 Pilot Light의 약점(데이터 동기화 지연)을 Global Tables로 해결한 것입니다.
4. 운영 복잡도 관리
Active-Active는 양쪽 리전에서 동시에 쓰기가 발생하여 데이터 일관성 관리가 복잡합니다. Pilot Light는 메인 리전만 활성화되므로 운영 복잡도가 낮고, 장애 시에만 DR 리전이 활성화되는 단순한 구조입니다.

5.3 비용 최적화 포인트

  • DR 리전 EC2 인스턴스: Pilot Light 상태에서는 Desired Capacity 0으로 운영
  • NAT Gateway: 필요 시에만 활성화 (Step 1에서 확인 및 활성화)
  • CloudWatch Logs: 보관 기간 최적화 (DR 리전은 짧은 보관 기간)
  • Reserved Instance: 메인 리전에만 적용, DR 리전은 On-Demand 사용
  • AMI 저장 비용: AWS Backup Lifecycle Policy를 통한 오래된 AMI 자동 삭제

6. 실제 운영에서 고려한 문제점과 해결 방식

6.1 Step Functions와 Terraform의 충돌 문제

문제: Step Functions State Machine 정의를 Terraform으로 관리하지만, 런타임에 Lambda 함수의 환경 변수나 IAM 역할이 변경될 수 있어 IaC와 충돌이 발생할 수 있습니다.

해결 방식:

  • Step Functions 정의는 Terraform으로 관리하되, 런타임 변수는 AWS Systems Manager Parameter Store에 저장
  • Lambda 함수는 Parameter Store에서 값을 읽어오도록 구현 (환경 변수 최소화)
  • IAM 역할 변경은 Terraform으로만 관리하여 일관성 유지
  • Step Functions 실행 중 State Machine 정의 변경 시에도 기존 실행에는 영향 없도록 설계

6.2 AMI 업데이트 전략

문제: DR 리전의 AMI가 오래되면 복구 시 애플리케이션 버전 불일치 또는 보안 패치 미적용 문제가 발생할 수 있습니다.

해결 방식:

  • AWS Backup을 통한 주간 AMI 생성 및 Cross-Region Copy 자동화
  • Step 2에서 최신 AMI를 자동으로 선택하도록 Lambda 함수 구현
  • AMI 태깅 전략: BackupType=DR, CreatedDate 태그로 관리
  • 정기적인 DR 테스트를 통한 AMI 유효성 검증

6.3 DynamoDB Global Tables의 최종 일관성

문제: Global Tables는 최종 일관성 모델이므로, 메인 리전에서 쓰기 직후 DR 리전으로 전환되면 데이터가 아직 복제되지 않았을 수 있습니다.

해결 방식:

  • RPO 목표를 5분으로 설정하여 최대 허용 데이터 손실 시간 명확화
  • 클라이언트 측 Retry 로직으로 일시적 데이터 부재 처리
  • 중요한 트랜잭션은 Idempotency Key를 사용하여 중복 처리 방지
  • 모니터링을 통한 복제 지연 시간 추적

6.4 Route 53 DNS 전파 지연

문제: Route 53 레코드 변경 후 DNS 전파가 완료되기까지 시간이 걸려, 일부 클라이언트는 여전히 메인 리전으로 요청을 보낼 수 있습니다.

해결 방식:

  • Route 53 TTL을 60초로 설정하여 전파 시간 최소화 (평소에도 짧은 TTL 유지)
  • CloudFront를 프론트엔드에 배치하여 DNS 조회 빈도 감소
  • Step 4에서 DNS 전파 완료를 기다리는 로직 포함 (CloudWatch Metric 기반 확인)
  • 메인 리전이 복구되더라도 일정 시간(예: 1시간) 동안 DR 리전으로 트래픽 유지 후 점진적 전환

6.5 Failback (메인 리전 복귀) 전략

문제: DR 리전으로 전환된 후 메인 리전이 복구되면, 안전하게 메인 리전으로 트래픽을 복귀(Failback)해야 합니다.

해결 방식:

  • 수동 Failback 프로세스:
    1. 메인 리전 Health Check 정상화 확인
    2. 메인 리전 인프라 복구 (필요 시)
    3. 데이터 동기화 상태 확인 (DynamoDB Global Tables 복제 지연 확인)
    4. Route 53 레코드를 메인 리전으로 점진적 전환 (Weighted Routing 활용)
    5. 모니터링을 통한 안정성 확인 후 100% 전환
  • 자동 Failback 옵션: EventBridge Rule을 통한 메인 리전 Health Check 복구 감지 → Step Functions Failback Workflow 실행 (운영팀 검토 후 선택적 사용)
운영 권장사항: Failback은 가능한 한 수동으로 수행하는 것을 권장합니다. DR 전환과 달리 비즈니스에 직접적인 영향을 주는 작업이므로, 운영팀이 데이터 동기화 상태를 확인하고 적절한 시점에 전환하는 것이 안전합니다.

6.6 DR 테스트 전략

DR 시스템은 정기적인 테스트 없이는 실제 장애 시 제대로 작동하지 않을 수 있습니다.

  • 월간 테스트: Step Functions Workflow 수동 실행을 통한 전체 프로세스 검증
  • 분기별 테스트: 실제 메인 리전을 일시적으로 차단하여 End-to-End 테스트
  • RTO/RPO 검증: 각 테스트마다 실제 복구 시간 및 데이터 손실 시간 측정
  • 문서화: 테스트 결과 및 개선 사항을 Runbook에 기록

7. 이 프로젝트를 통해 보여주고 싶은 엔지니어링 역량

7.1 엔터프라이즈 아키텍처 설계 능력

단순히 AWS 서비스를 나열한 것이 아니라, 비즈니스 요구사항(RTO/RPO, 비용)을 분석하고 이를 만족하는 최적의 아키텍처를 설계했습니다. Pilot Light, Warm Standby, Active-Active 전략을 비교 분석하여 프로젝트에 가장 적합한 방식을 선택한 점은 시니어 아키텍트 수준의 판단력입니다.

7.2 자동화 및 오케스트레이션 역량

Step Functions를 활용한 복잡한 멀티 스텝 워크플로우 설계와, Lambda 함수를 통한 각 단계의 실행 로직 구현은 서버리스 아키텍처에 대한 깊은 이해를 보여줍니다. 또한 Lock 메커니즘, 승인 절차, 롤백 로직 등 운영 안정성을 고려한 설계를 포함했습니다.

7.3 Infrastructure as Code 역량

Terraform을 통한 Main/DR 리전 인프라 분리 관리, S3 Backend + DynamoDB Lock을 통한 State 파일 관리, 모듈화를 통한 코드 재사용은 실무 수준의 IaC 운영 역량을 보여줍니다. 특히 Step Functions와 Terraform의 충돌 문제를 Parameter Store로 해결한 점은 실제 운영 환경에서 발생하는 문제를 인식하고 해결하는 능력을 보여줍니다.

7.4 운영 관점의 사고

이 프로젝트는 단순 구현을 넘어서 실제 운영에서 발생할 수 있는 문제점을 사전에 고려했습니다:

  • 비용 최적화를 위한 Pilot Light 전략 선택 및 세부 최적화 포인트
  • DR 테스트 전략 및 Runbook 작성
  • Failback 프로세스 설계
  • 모니터링 및 알림 체계 구축
  • 자동화와 안전성의 균형 (승인 절차 포함)

7.5 데이터 일관성 및 복제 전략 이해

DynamoDB Global Tables의 최종 일관성 모델을 이해하고, 이를 RPO 목표 달성에 활용하면서도 발생할 수 있는 문제점을 인식하고 해결 방안을 제시했습니다. 또한 S3 Cross-Region Replication을 통한 정적 웹 자산 복제 전략도 포함했습니다.

7.6 글로벌 트래픽 관리 역량

Route 53 Failover Routing, CloudFront Origin Group을 활용한 글로벌 트래픽 전환 전략은 DNS 및 CDN에 대한 깊은 이해를 보여줍니다. DNS TTL 최적화, 전파 시간 고려 등 실무에서 중요한 세부 사항까지 고려했습니다.

종합 평가
이 프로젝트는 AWS 공인 솔루션 아키텍트 수준의 지식을 바탕으로, 실제 엔터프라이즈 환경에서 사용 가능한 수준의 DR 아키텍처를 설계했습니다. 단순히 기술을 나열한 것이 아니라, 비즈니스 요구사항 분석 → 아키텍처 설계 → 구현 → 운영 고려사항까지 전체 라이프사이클을 고려한 엔지니어링 역량을 보여줍니다.

8. 프로젝트 마무리

MegaTicket Pilot Light DR 프로젝트를 통해 엔터프라이즈급 재해 복구 시스템의 설계와 구현 과정을 경험했습니다. 이 프로젝트는 실제 운영 환경에서 바로 사용 가능한 수준의 아키텍처를 목표로 했으며, 비용, 성능, 안정성, 운영 복잡도를 종합적으로 고려한 설계를 포함합니다.

향후 개선 사항으로는 AI/ML 기반 이상 탐지(Anomaly Detection)를 통한 사전 장애 감지, Chaos Engineering을 통한 DR 시스템 검증, Multi-Region Active-Active로의 전환 등이 있습니다.
